## 1. 系统设计

### 1.1 总体架构

```
浏览器（静态 HTML + 原生 JS）
   │  HTTP + JSON，请求头 Authorization: Bearer <JWT>
   ▼
FastAPI
   ├─ routers/   路由层：参数解析、鉴权、HTTP 状态码
   ├─ services/  业务层：问卷管理、提交、统计
   ├─ engine/    规则引擎：校验引擎、跳转引擎（纯函数，不访问数据库）
   └─ db.py      PyMongo 连接
   ▼
MongoDB：users / surveys / responses / participations
```

- 登录用 JWT，无状态，不需要另外的会话存储（满足 C1、C2，对应 X15）。
- 校验规则和跳转规则以**数据**形式存在问卷文档里。引擎只是通用的解释器，按题型和 op 查表执行，不为某份问卷写专门代码（满足 C8、D3）。

### 1.2 代码结构

```
app/
  main.py            创建应用，挂载路由和静态页面
  config.py  db.py
  security.py        bcrypt 密码哈希；JWT 签发与校验
  deps.py            "当前登录用户"依赖
  models.py          请求 / 响应的 Pydantic 模型
  routers/           auth.py  surveys.py  questions.py  fill.py  stats.py
  services/          surveys.py  submissions.py  stats.py
  engine/            validation.py  jump.py
db/
  schema.py          四个集合的 $jsonSchema 与索引（即提交物中的 MongoDB schema）
  init_db.py         建集合、更新校验器、建索引；可重复执行
static/              login.html  surveys.html  edit.html  fill.html  stats.html（含 js / css）
tests/
docs/
```

### 1.3 角色与权限

| 操作 | 谁可以 |
|---|---|
| 注册、登录 | 任何人 |
| 创建问卷；管理自己的问卷；看统计 | 登录用户，且只能操作自己创建的问卷（F1.7、F6.7）。访问别人的问卷一律返回 404，不暴露问卷是否存在 |
| 打开问卷链接、填写、提交 | 任何登录用户（F2.7、X1）；问卷须为已发布且未过截止时间 |
| 看到答卷是谁填的 | 只有非匿名问卷的创建者能看到 |

### 1.4 问卷状态

```
          publish             close
 draft ───────────► published ───────► closed
                        ▲                 │
                        └──── reopen ─────┘
```

- **draft（草稿）**：可以增删改题目、设置跳转；不能填写。
- **published（已发布）**：可以填写。设了截止时间且已过 → 拒绝提交。"已截止"是用 `deadline` 和当前时间算出来的，不单独存一个状态：这样不需要定时任务去改状态，也不会出现状态和时间对不上。
- **closed（已关闭）**：拒绝提交，统计照常能看。
- **reopen（重新开放）**：适用于已关闭的问卷，也适用于已发布但已过截止时间的问卷。状态回到 published，并要求截止时间为空或在未来（X11）。
- **发布条件**：至少 1 道题；所有跳转规则合法。
- **发布后锁定（X10，2026-10-19 本人调整）**：发布即确定，标题、说明、题目、是否匿名、是否允许多次填写**全部不能再改**；发现问题就删除问卷、重新创建发布。只保留"控制收不收答卷"的操作：关闭、重新开放（重新开放时可以设新的截止时间）。
- **删除（2026-10-19 本人设计）**：任何状态的问卷都可以删除，已收到的答卷随之无法再查看。采用标记删除：在问卷上写入 `deletedAt`，之后列表不显示、链接打不开、统计看不到、不能再提交；数据仍留在库里。标记删除只改一个文档，不存在跨集合删到一半的问题，误删时管理员也能恢复。
- **状态切换以时间先后为准**：发布、关闭、重开、删除、修改草稿全部用"条件更新"——把"当前状态是否允许"和"修改"合成一条数据库命令（单文档原子操作），晚到的、已不满足条件的操作直接失败并返回原因，不会出现"判断时还是草稿、写入时已经发布"的情况。

### 1.5 填写与提交流程

1. 填写者登录后打开分享链接 `/survey/{slug}`，前端调用 `GET /api/fill/{slug}` 拿到问卷。
2. 每答完一题，前端调用 `POST /api/fill/{slug}/navigate`，带上目前的全部答案。服务端返回答题路径、下一题和当前错误，前端据此显示下一题或错误提示（F4.5、F5.2–F5.4）。**跳转逻辑只在服务端实现一份**，前端不重复实现。
3. 提交时调用 `POST /api/fill/{slug}/responses`，服务端依次：
   1. 检查问卷可以填写：状态为 published，且没过截止时间；
   2. 从第一题起，按跳转规则重新算出答题路径；
   3. 对路径上的题逐题校验：必答题没答、或答案不合规则 → 报错；答了路径外的题 → 拒绝（X8）；
   4. 在 participations 里登记（不允许多次填写时，由唯一索引拦截重复）；
   5. 写入 responses（匿名问卷不写 `respondentId`）；
   6. 返回 201，只返回提交时间（填写者不能查看自己的答卷）。
4. 打开链接时（2026-10-20 确认）：草稿 → 404，对外当作不存在；发布过又删除 → 410"问卷已删除"；已关闭 / 已截止 → 200，照常返回标题和说明，并标明不能填写及原因；问卷不允许多次填写且本人已填过 → 一打开就标明"你已经填写过这份问卷"。填写视图不返回跳转规则。
5. 关闭问卷与提交同时发生时，以提交时检查那一刻为准：问卷还开着就算数（两个集合无法用一条命令同时完成，本机也不支持跨集合事务）。

### 1.6 API 清单

状态码约定：401 未登录；404 不存在或不是自己的问卷；409 状态冲突（已锁定、已填写过、已关闭等）；410 问卷已删除（填写链接）；422 输入不合法。提交答卷的 422 按题目分开返回：`{"message": "提交内容有误", "errors": {题目 id: 提示}}`。请求格式错误（缺字段、多字段、类型不对、时间不带时区等）的 422 为 `{"detail": [{"type", "loc", "msg"}]}`，提示统一为中文（`app/errors.py`），且不回显原始输入，避免把密码等内容发回。

静态 HTML + 原生 JS，由后端直接提供（`app/main.py` 挂载 `/static`；`/` 跳到"我的问卷"；`/survey/{slug}` 返回填写页）。

| 页面 | 文件 | 功能 |
|---|---|---|
| 登录 / 注册 | `static/login.html` | 两个标签页；注册成功后自动登录；登录后回到 `?next=` 指定的本站页面 |

- 截止时间用浏览器的日期时间选择器，提交时转为带时区的 ISO 时间。

## 2. MongoDB 设计

### 2.1 集合划分（D1）

| 集合 | 存什么 | 一条文档代表 | 增长特点 |
|---|---|---|---|
| `users` | 账号 | 一个用户 | 慢 |
| `surveys` | 问卷，内嵌题目、选项、校验规则、跳转规则 | 一份问卷的完整定义 | 慢；单份文档大小有上限 |
| `responses` | 答卷，内嵌各题答案 | 一次提交 | 快，没有上限 |
| `participations` | 谁填过哪份问卷、填了几次 | 一个（问卷, 用户）组合 | 与填写人数同级 |

引用关系：

```
users._id ◄── surveys.ownerId
surveys._id ◄── responses.surveyId
users._id ◄── responses.respondentId     （仅非匿名问卷）
surveys._id, users._id ◄── participations.surveyId, participations.userId
```

### 2.2 嵌入还是引用（D4）

| 关系 | 选择 | 理由 |
|---|---|---|
| 问卷 → 题目、选项、规则 | 嵌入 | 打开、填写、校验、统计都需要整份定义，总是一起读；题目数量有限（几十道题只有几十 KB，远低于 16MB 上限）；发布后整体锁定，不存在单独高频修改某道题的情况；一次读取拿到全部，单文档更新天然是原子的 |
| 问卷 → 答卷 | 引用（`responses.surveyId`） | 答卷数量没有上限。嵌进问卷会让问卷文档无限增长、逼近 16MB；多人同时提交还会争抢同一个文档（F5.7） |
| 答卷 → 各题答案 | 嵌入 | 一次提交是一个整体：一次写入，一起读取 |
| 问卷 → 创建者 | 引用（`ownerId`） | 用户独立存在，一个用户对应多份问卷 |
| 谁填过 | 单独集合 `participations` | 匿名问卷的答卷不能带用户 id（X1），但创建者关闭多次填写时，"每人只能填一次"又必须知道谁填过（X3）。把"谁填过"和"填了什么"分开存，两边都只通过 surveyId 关联，无法把某个人对应到某份答卷 |

**冗余的取舍（D2）**

- 答卷只存题目 id 和选项 id，不复制题目标题和选项文字；统计展示时再从问卷文档取。这样做的前提是发布后题目结构锁定（X10），id 总能找到对应的题目和选项。
- 不在问卷文档里维护"已选人数"这类计数字段，统计时实时聚合。好处是多人同时提交不会争抢同一个文档，计数也不会和答卷对不上。代价是每次看统计都要扫一遍该问卷的答卷，课程规模下可以忽略；如果阶段二答卷量很大，再考虑预先计算。
- 唯一有意保留的重复是 `participations.count`。非匿名问卷的提交次数能从 responses 数出来，但匿名问卷的答卷里没有用户 id，数不出来，所以需要这个字段。

### 2.3 文档结构

所有文档都带 `schemaVersion`（当前为 1），以后结构变化时，迁移脚本按版本号升级（见 2.12）。

**users**

```js
{
  _id: ObjectId("..."),
  schemaVersion: 1,
  username: "zhangsan01",             // 账号：登录用，唯一，3–32 位字母 / 数字 / 下划线，区分大小写
  displayName: "张三",                 // 名字：展示用，可重复，1–32 个字符
  passwordHash: "$2b$12$...",         // bcrypt 哈希，不存明文（X14）
  createdAt: ISODate("2026-10-15T08:00:00Z")   // 注册时间（F1.6）
}
```

账号与名字分开（2026-10-19 本人设计）：账号对应原文的"用户名"，只用于登录并保证唯一；名字只用于展示，允许重名。需要区分重名的地方（如统计里的填写者）显示为"名字（账号）"。

密码规则（2026-10-19 本人设计）：8–72 位，只允许英文字母、数字和英文符号（可打印 ASCII 字符，不含空格），不能有汉字。上限 72 是 bcrypt 能处理的最大字节数；只允许 ASCII 字符后一个字符就是一个字节，所以 72 个字符正好用满。

**surveys**（示例题目取自作业原文）

```js
{
  _id: ObjectId("..."),
  schemaVersion: 1,
  revision: 7,                         // 修改版本号：每次修改加 1，写回时用作乐观锁条件（见 2.9）
  ownerId: ObjectId("..."),            // → users._id
  title: "大学生生活调查",
  description: "约 2 分钟",
  slug: "k3X9pQ2a",                    // 分享链接 /survey/k3X9pQ2a，8 位随机字母数字，唯一
  status: "published",                 // draft | published | closed
  settings: {
    allowAnonymous: false,             // F2.1
    allowMultipleSubmissions: true,    // X2：默认允许，创建者可以关闭
    deadline: ISODate("2026-11-01T00:00:00Z")  // 可为 null
  },
  questions: [
    {
      id: "q_a0000001", type: "single_choice", title: "你的性别", required: true,
      options: [
        { id: "o_b0000001", label: "男" },
        { id: "o_b0000002", label: "女" },
        { id: "o_b0000003", label: "其他" }
      ],
      jumpRules: [
        { when: { op: "eq", value: "o_b0000003" }, goto: "q_a0000004" }   // 选"其他"跳到第 4 题
      ]
    },
    {
      id: "q_a0000002", type: "multiple_choice", title: "你喜欢的水果", required: true,
      options: [
        { id: "o_c0000001", label: "苹果" }, { id: "o_c0000002", label: "香蕉" },
        { id: "o_c0000003", label: "西瓜" }, { id: "o_c0000004", label: "葡萄" }
      ],
      validation: { minSelect: 2, maxSelect: 3 }
    },
    {
      id: "q_a0000003", type: "number_input", title: "年龄", required: true,
      validation: { min: 0, max: 120, integer: true },
      jumpRules: [
        { when: { op: "lt", value: 18 }, goto: "END" }                     // 未成年直接结束
      ]
    },
    {
      id: "q_a0000004", type: "text_input", title: "你的建议", required: false,
      validation: { minLength: 5, maxLength: 200 }
    }
  ],
  createdAt: ISODate("..."), updatedAt: ISODate("..."),
  publishedAt: ISODate("..."), closedAt: null
  // 被删除的问卷另有 deletedAt: ISODate("...")；未删除的没有这个字段
}
```

**responses**

```js
// 非匿名问卷：路径 第1题 → 第2题 → 第3题 → 第4题
{
  _id: ObjectId("..."), schemaVersion: 1,
  surveyId: ObjectId("..."),           // → surveys._id
  respondentId: ObjectId("..."),       // → users._id；匿名问卷没有这个字段
  submittedAt: ISODate("..."),
  answers: [                           // 只含答题路径上实际作答的题，按路径顺序
    { questionId: "q_a0000001", value: "o_b0000001" },                  // 单选：选项 id
    { questionId: "q_a0000002", value: ["o_c0000001", "o_c0000003"] },  // 多选：选项 id 数组
    { questionId: "q_a0000003", value: 20 },                            // 数字
    { questionId: "q_a0000004", value: "希望食堂多开几个窗口" }          // 文本
  ]
}

// 匿名问卷：第1题选"其他"，按规则跳过第2、3题
{
  _id: ObjectId("..."), schemaVersion: 1,
  surveyId: ObjectId("..."),
  submittedAt: ISODate("..."),
  answers: [
    { questionId: "q_a0000001", value: "o_b0000003" },
    { questionId: "q_a0000004", value: "没有建议，谢谢" }
  ]
}
```

答案用 `[{questionId, value}]` 数组，而不是以题目 id 作键的对象 `{ "q_a0000001": ... }`：动态键名没法建索引、没法用校验器约束，聚合时也得先转换；数组可以直接 `$unwind` 后按 `questionId` 分组。

**participations**

```js
{
  _id: ObjectId("..."), schemaVersion: 1,
  surveyId: ObjectId("..."),
  userId: ObjectId("..."),
  count: 1                             // 该用户对该问卷的提交次数
}
```

### 2.4 题型与校验规则的存储

题型和原文的对应：原文的"填空题"分"文字或数字"两种，这里拆成 `text_input` 和 `number_input` 两个题型。这样每个题型的字段是固定的，校验器能逐个题型约束。

| `type` | 原文 | `options` | `validation` 字段 | 答案 `value` |
|---|---|---|---|---|
| `single_choice` | 单选题 | ≥ 2 个 | 无 | 选项 id（字符串） |
| `multiple_choice` | 多选题 | ≥ 2 个 | `minSelect`、`maxSelect` | 选项 id 数组，不重复 |
| `text_input` | 文本填空 | 无 | `minLength`、`maxLength` | 字符串 |
| `number_input` | 数字填空 | 无 | `min`、`max`、`integer` | 数字 |

所有题型都有 `required`（F3.6）。

- **必答**：`required: true` 表示该题在答题路径上就必须作答。`required: false` 可以不答，但一旦作答，答案就要满足 `validation`。
- **多选数量**："至少 2 个 / 最多 3 个 / 必须 2 个"分别存成 `minSelect: 2` / `maxSelect: 3` / `minSelect: 2, maxSelect: 2`。两个字段就能表达三种需求，也不会出现"必须 2 个又至少 3 个"这种矛盾组合。
- **字数**：按字符数计，一个汉字算 1。
- **手机号**（X13）：用 `number_input` 加 `integer: true`。11 位数超过 32 位整数范围，存为 64 位整数，已验证可行。
- **保存题目时应用层还要检查**：选项 id 不重复；`minSelect ≤ maxSelect ≤ 选项数`；`min ≤ max`；`minLength ≤ maxLength`。
- **校验引擎**：两张对照表。一张按 `type` 找到答案类型检查，另一张按 `validation` 的每个键找到对应检查函数；错误信息用中文，按题目 id 返回。

### 2.5 跳转规则的存储与求值

跳转规则存在**来源题**上：`jumpRules` 数组，每条为 `{ when: { op, value }, goto }`。`goto` 是目标题的 id，或者 `"END"`（结束问卷）。

| 题型 | `op` | `value` | 命中条件 |
|---|---|---|---|
| 单选 | `eq` | 选项 id | 选了这个选项 |
| 单选 | `in` | 选项 id 数组 | 选了其中任一个 |
| 多选 | `containsAny` | 选项 id 数组 | 至少选了其中一个 |
| 多选 | `containsAll` | 选项 id 数组 | 这些全都选了 |
| 多选 | `equals` | 选项 id 数组 | 选的恰好就是这些 |
| 数字 | `eq` `ne` `gt` `gte` `lt` `lte` | 数字 | 等于 / 不等于 / 大于 / 大于等于 / 小于 / 小于等于 |
| 数字 | `between` | `[a, b]` | a ≤ 值 ≤ b |
| 文本 | — | — | 不支持跳转（F4 只要求单选、多选、数字） |

原文例子"第 1 题选 A → 跳到第 5 题；选 B → 跳到第 3 题"存成：

```js
jumpRules: [
  { when: { op: "eq", value: "<A 的选项 id>" }, goto: "<第 5 题的 id>" },
  { when: { op: "eq", value: "<B 的选项 id>" }, goto: "<第 3 题的 id>" }
]
```

**求值方法**

1. 从第一题开始。
2. 当前题如果作答了，按 `jumpRules` 的顺序逐条判断，**第一条命中的生效**，跳到它的 `goto`。
3. 没有规则命中，或者这题没作答 → 进入顺序上的下一题。
4. `goto` 是 `END`，或已经过了最后一题 → 结束。
5. 走过的题组成"答题路径"；必答检查和答案校验只针对路径上的题。

**保存规则时检查（应用层）**：`goto` 指向的题存在，且位于来源题**之后**（只能往后跳，因此不会形成死循环，X7）；`value` 里的选项 id 都属于本题；`between` 的 a ≤ b。`op` 与题型是否匹配，数据库校验器也会检查。

**整份检查**（`app/engine/structure.py` 的 `check_survey`）：每次修改题目写回前、以及发布前，都对整份问卷检查一遍题目定义和全部跳转规则，错误信息指明"第几题、第几条规则、什么问题"。

**修改会让已有规则失效时，一律拒绝并说明原因，不自动改动用户的配置**（2026-10-20 确认）：

| 操作 | 什么情况下拒绝 | 状态码 |
|---|---|---|
| 设置跳转规则 | 规则本身不合法（往前跳、目标不存在、条件与题型不匹配、用了别的题的选项等） | 422 |
| 删除题目 | 有别的题的规则跳到它，提示是哪几道题 | 409 |
| 调整顺序 | 某条规则因此变成往前跳 | 409 |
| 修改题目 | 删掉的选项被本题规则用到；或本题已有规则时改题型 | 409 |

修改题目时，原有选项提交时带上 id、新选项不带，服务器保留原 id，因此改选项文字不影响规则。

**填写时的答案约定与引擎**（2026-10-20 确认，实现见 `app/engine/validation.py`、`app/engine/jump.py`）

- 填写页一题一页。答案以 `{题目 id: 值}` 传给引擎：**没有这道题 = 还没答到**；值为 `null`、空字符串或空数组 = 看过、不答（非必答题点"下一题"时传 `null`，必答题会提示"此题为必答题"）。
- 校验引擎按题型查表检查。数字只接受数字类型，`"18"` 这样的字符串不接受；要求整数时 `18.0` 视为 18；文本去掉首尾空格后计字数（一个汉字算 1），只有空格视为不答；多选重复选同一项报错，保存时按选项原本的顺序排列。
- 跳转引擎按上面的求值方法走路径。已答的题不合规时，路径停在这道题（答案不对就无法决定往哪跳）。
- 两个入口：
  - `navigate`（填写过程中）：返回路径、下一题、已答题的错误。改了前面的答案导致后面的答案不在路径上时，只把这些题列出来提示前端清掉，不算错误。
  - `evaluate_submission`（提交时）：从头重算，路径上没传的题按"不答"处理；答了路径外的题、不存在的题都记为错误；全部通过才保存，只保存路径上实际作答的题。

**为什么这样存**

- 规则是问卷定义的一部分：和题目一起读取、一起锁定，放在来源题上最直观。
- 用题目 id 而不是题号（X9）：插入题目或调整顺序后，规则不会失效。
- `when` 是扩展点：如果阶段二要求"第 1 题选 A 且第 3 题大于 5"，可以扩展成 `when: { all: [ {questionId, op, value}, ... ] }`，引擎加一个组合判断即可，现有规则照样有效。

| 集合 | 索引 | 类型 | 服务的查询 |
|---|---|---|---|
| users | `{ username: 1 }` | 唯一 | 登录时按账号查找；保证账号不重复 |
| surveys | `{ slug: 1 }` | 唯一 | 通过分享链接打开问卷；保证链接不重复 |
| surveys | `{ ownerId: 1, createdAt: -1 }` | 普通 | "我的问卷"列表：按创建者过滤、按时间倒序，一个索引同时覆盖过滤和排序 |
| responses | `{ surveyId: 1, submittedAt: -1 }` | 普通 | 统计聚合的 `$match`；填空题内容按时间分页 |
| participations | `{ surveyId: 1, userId: 1 }` | 唯一 | 判断某人是否填过；并发提交时由唯一约束防止重复 |

暂不对 `answers.questionId` 建多键索引：统计总是先按 `surveyId` 过滤，单份问卷的答卷量在课程规模下很小。

### 2.7 校验器：两层分工

| 层 | 负责 | 例子 |
|---|---|---|
| 数据库（`$jsonSchema`，`validationLevel: "strict"`，`validationAction: "error"`） | 结构与类型 | 必填字段、字段类型、状态枚举、id 格式；题型与字段的对应（按 `type` 用 `oneOf` 分支）；跳转 `op` 必须与题型匹配；文本题不能有跳转规则；答案值只能是字符串、数字或数组 |
| 应用层 | 跨字段、跨文档、依赖具体问卷的语义 | `minSelect ≤ maxSelect`；选项 id 唯一；`goto` 指向存在且靠后的题；答卷内容是否满足该问卷各题的规则（每份问卷规则不同，数据库校验器无从得知） |

两层都要：数据库校验器是最后一道防线，挡住程序 bug 或手工在 mongosh 里写入的坏数据；应用层负责给用户友好的逐题错误提示。

### 2.8 统计（F6）

整份问卷的统计用一次聚合完成（已在临时库中跑通）：

```js
db.responses.aggregate([
  { $match: { surveyId: <问卷 id> } },
  { $unwind: "$answers" },
  { $facet: {
      // 每道题有多少份答卷作答了
      answered: [
        { $group: { _id: "$answers.questionId", n: { $sum: 1 } } }
      ],
      // 选择题每个选项被选次数（单选的值是字符串，$unwind 当作单元素处理；多选的值是数组，被展开）
      optionCounts: [
        { $match: { "answers.questionId": { $in: <选择题 id 列表> } } },
        { $unwind: "$answers.value" },
        { $group: { _id: { q: "$answers.questionId", o: "$answers.value" }, n: { $sum: 1 } } }
      ],
      // 数字题平均值
      numberAvg: [
        { $match: { "answers.questionId": { $in: <数字题 id 列表> } } },
        { $group: { _id: "$answers.questionId", avg: { $avg: "$answers.value" }, n: { $sum: 1 } } }
      ]
  } }
])
```

- 另用 `countDocuments({ surveyId })` 得到问卷的总提交数。
- 应用层把聚合结果和问卷定义合并：补上选项文字，没人选的选项补 0。
- 填空题内容按单题分页查询：`$match` → `$unwind` → 按题目过滤 → 按提交时间倒序 → `$skip` / `$limit`。非匿名问卷再 `$lookup` users，带上填写者的"名字（账号）"。
- **统计口径（X12）**：单选的"回答人数"指作答了这道题的答卷数（因为有跳转，可能少于问卷总提交数），同时给出问卷总提交数；多选是每个选项被选的次数。

**实现（2026-10-20 确认，`app/services/stats.py`）**

- 分工：MongoDB 聚合管道负责"算"（筛选、展开、分组、计数、平均值、最新几条），Python 负责"拼"（补选项文字、没人选的补 0、算占比、保留 2 位小数）。
- 整份统计 = 一次 `$facet` 聚合（四路：每题回答人数、选项计数、数字题平均 / 最小 / 最大、填空题最新 5 条〔`$firstN`〕）+ 一次 `countDocuments` 总提交数 + 一次查 users 带出最新几条的填写者。
- 占比的分母是"回答了这道题的人数"，多选各项相加可超过 100%。
- 单题统计：填空题按页码分页（默认每页 20 条，最多 100 条），按提交时间倒序，同一毫秒内按 `_id` 区分先后；非匿名问卷用 `$lookup` 关联 users，显示"名字（账号）"。
- 只有创建者能看；已关闭、已截止照常能看；已删除返回 404。
- **索引验证**：测试用 `explain` 检查两条统计管道，执行计划为 `IXSCAN survey_submittedAt → FETCH → SORT`，没有 COLLSCAN。其中的 SORT 来自"同一毫秒按 `_id` 区分先后"这一排序条件，只对已筛出的该问卷答卷做内存排序；若答卷量很大，可把索引扩展为 `{surveyId, submittedAt: -1, _id: -1}` 让索引直接提供顺序。

### 2.9 并发与一致性

- **多人同时填写（F5.7）**：每次提交只插入一条新文档，不修改任何共享文档（问卷里没有计数字段），所以没有写冲突。
- **多次填写（F5.9、X2）**：默认允许。这时每次提交都直接记一条答卷，participations 只把该用户的 `count` 加 1，不做任何拦截。
- **创建者关闭了多次填写时**：靠 participations 的唯一索引防止同一人重复提交。两个请求同时提交时，只有一个能插入成功，另一个收到重复键错误（E11000），返回"已填写过"。
- **两步写入没有放进事务**（只影响关闭了多次填写的问卷）：本机 MongoDB 默认以单机模式运行，不支持多文档事务（事务需要副本集）。做法是先登记 participations，再写 responses；写 responses 失败就撤回登记（删除，或把 `count` 减 1）。最坏情况是进程恰好在两步之间崩溃，结果是"登记了但没有答卷"，不会出现重复答卷。改用单节点副本集就能用事务，见第 3 节第 5 条。
- **发布后结构锁定**：保证统计时的题目定义与答卷一致。
- **编辑题目用乐观锁**（2026-10-20 确认）：题目之间有引用，检查要看整份问卷，所以题目的增、改、删、调序、设规则都按"读出问卷 → 代码里修改 → 整份检查 → 写回"进行。写回时带上条件 `revision` 等于读出时的值，并把 `revision` 加 1；如果中间有别的修改插进来，`revision` 已变，写回失败，返回"问卷刚被修改过，请刷新后重试"。发布同样带 `revision` 条件，保证发布的正是刚检查过的那一版。这样不需要锁住问卷，也不需要事务，就能做到"以先到者为准"。

### 2.10 为什么不用关系数据库的结构（D5）

同样的数据放进关系库，至少需要：users、surveys、questions、options、jump_rules（及条件表）、responses、answers，以及多选用的 answer_options。问题在于：

- **打开问卷**：一份问卷要 join 四五张表，再在应用层拼回树形结构。
- **题型字段不同**：要么 questions 表里大量可空列（min_select、max_length、min_value、is_integer……），要么每种题型一张表；新增题型就得改表结构。
- **答案类型不同**：值可能是选项、数组、文本或数字，要么拆成多列（value_text / value_number / option_id），要么用 EAV（实体-属性-值）模式；统计 SQL 会很绕。
- **多选答案**：一个值是数组，只能拆到子表。

在 MongoDB 里，一份问卷就是一个文档，读写方式和使用方式一致；答案的值天然可以是多种类型，数组直接存。

### 2.11 为什么适合 MongoDB（D6）

- **结构匹配**：问卷是树形的、按题型变化的结构。文档模型加数组嵌入，一次读写就能拿到或存下整份问卷。
- **灵活又可约束**：灵活的 schema 允许不同题型有不同字段，`$jsonSchema` 校验器又能在数据库层把结构管住。
- **统计在库内完成**：聚合管道（`$unwind` / `$group` / `$facet` / `$lookup`）可以直接在数据库里算统计。
- **适应需求变化**：阶段二新增字段不用停机改表。每个文档带 `schemaVersion`，可以按版本逐步迁移（Schema Versioning 模式）。
- **写入模式合适**：答卷只追加、不修改，适合高并发插入。

### 2.12 为阶段二预留的扩展点

- **`schemaVersion`**：结构变化时，迁移脚本按版本升级；迁移期间可以把校验器临时设为 `validationLevel: "moderate"`。
- **新题型**：校验器 `oneOf` 加一个分支，校验引擎、跳转引擎、统计各加一个函数，已有数据不受影响。
- **跳转条件**：可以按 2.5 末尾说的方式扩展成组合条件。
- **稳定 id**：题目和选项的 id 不随顺序变化。如果阶段二要把题目抽成独立集合（比如题库），可以直接沿用。
- **git tag**：阶段一提交时打 tag，阶段二报告中的"改了哪些部分"可以直接对照 diff 说明。

## 4. 阶段二：需求变更与设计演进

> 2026-10-26 开始。需求来源：老师发布的《需求变更说明》，编号 N1–N8；决定 Y1–Y7 由本人确认，全部按推荐方案执行。阶段一的提交点为 git tag `v1-stage1`。

### 4.1 新需求与阶段一设计的矛盾

| 编号 | 需求 | 阶段一的设计为什么不够 |
|---|---|---|
| N1 | 保存常用题目，建问卷时选用，一题多卷 | 题目内嵌在问卷里，id 只在本问卷内有效，离开问卷就不存在 |
| N2 | 题目共享给其他用户 | 题目没有独立的所有者和访问控制 |
| N3 | 已发布问卷的题不能改，改题应生成新题 | 发布后锁定已满足（X10）；但没有"生成新题"的概念 |
| N4 | 历史版本、改自哪个版本、恢复旧版本 | `revision` 只是乐观锁计数，不保留旧内容 |
| N5 | 同一题的多个版本并存，不同问卷用不同版本 | 同上 |
| N6 | 查看题目被哪些问卷使用 | 题目之间没有跨问卷的身份，无从查起 |
| N7 | 题库：管理、加题、选题、题库里的题可升级 | 没有 |
| N8 | 单道题跨问卷统计 | 统计管道以一份问卷为单位 |

核心矛盾：阶段一把题目当作问卷的一部分，阶段二要求题目成为可复用、可共享、有版本的独立实体。

### 4.2 设计决定（Y1–Y7）

| # | 决定 | 放弃的方案 |
|---|---|---|
| Y1 | **快照 + 引用**：问卷里仍存题目完整内容，另加 `source` 指向来源版本。版本不可变，快照永远与来源一致；填写、校验、跳转、按问卷统计、答卷结构都不用改 | 问卷只存引用，每次填写 / 统计都 `$lookup` 取内容，三个引擎和旧数据都要改 |
| Y2 | **题目与版本分成两个集合**：`questions` 存可变的部分（所有者、共享、最新版本摘要），`question_versions` 每个版本一个文档、只插入不修改 | 版本数组内嵌在题目里：无限增长，且问卷要单独引用某个版本 |
| Y3 | **版本一律不可变**：题库里保存修改 = 新版本；恢复旧版本 = 用旧内容生成新版本；可基于任意版本创建新版本（版本树）。问卷里改一道来自题库的题时，选择"另存为新版本并使用"或"只改本问卷（脱钩，记 `derivedFrom`）" | 未被使用的版本允许原地覆盖：草稿里的快照会与版本不一致 |
| Y4 | 同一道题的新版本只有创建者能加；改别人共享的题先"复制为我的题"，新题记 `derivedFrom` | 允许被共享者直接加版本 |
| Y5 | 题目级、题库级两级共享（按账号）；被共享者可用、可看历史、可复制，不能加版本、不能删；题库引用题目而非固定版本 | 只做一级共享 |
| Y6 | "被哪些问卷使用"：自己的问卷列详情，别人的问卷只给各版本的数量 | 列出所有问卷详情（暴露他人问卷，违背 F1.7） |
| Y7 | 跨问卷统计只统计自己的问卷；默认合并全部版本（按选项 id 合并），可按版本筛选；数字题增加分布 | 统计所有用到该题的问卷（共享题创建者能看到他人数据） |

### 4.3 数据结构的变化（第 1 段，2026-10-26 确认 ①B ②C ③A ④A ⑤A）

**新增集合**（完整校验器见 [db/schema.py](../db/schema.py)；附录 A 为阶段一版本）：

```js
// questions：题目本身（可变部分）
{ _id, schemaVersion: 1, ownerId,
  latest: { versionId, version, type, title },          // 最新版本摘要（冗余，可由版本集合重算）
  derivedFrom: { questionId, versionId, version } | null, // 复制自哪道题的哪个版本
  sharedWith: [userId],                                  // 最多 100 人，不可重复
  createdAt, updatedAt, deletedAt? }

// question_versions：每个版本一个文档，只插入不修改
{ _id, schemaVersion: 1, questionId, version,            // (questionId, version) 唯一
  parentVersionId: ObjectId | null,                       // 基于哪个版本创建，组成版本树
  kind: "create" | "edit" | "restore" | "fork",
  content: { type, title, required, options?, validation? },  // 无题目 id、无跳转规则
  note, createdBy, createdAt }

// question_banks：题库
{ _id, schemaVersion: 1, ownerId, name, description,
  items: [{ questionId, addedAt }],                       // 最多 500 条；引用题目，显示最新版本
  sharedWith: [userId], createdAt, updatedAt, deletedAt? }

// migrations：已执行的结构迁移
{ _id: "002_surveys_question_source", appliedAt, modified }
```

**`surveys` 的变化**：题目可带两个可选字段，结构版本 1 → 2。

- `source: { questionId, versionId, version }`：来自题库，且内容与该版本完全相同。被哪些问卷使用（N6）、跨问卷统计（N8）只看这个字段。
- `derivedFrom`：同样形状，表示来自题库但在本问卷里改过（已脱钩），内容已不同，不参与合并统计。
- 阶段一的题没有这两个字段，含义是"本问卷自建题"。

**几个设计要点**：

- **校验器复用（⑤A）**：题目内容的约束（四种题型的 `oneOf` 分支）抽成公共片段，问卷里的题与版本的 `content` 共用；版本内容设 `additionalProperties: false`，不允许带题目 id 和跳转规则——跳转规则引用的是同一问卷里的其他题，属于问卷上下文，不属于题目本身。
- **题库内嵌引用数组（③A）**：打开题库只读一个文档；加题 / 移除用 `$addToSet` / `$pull`，单文档原子，不需要事务。不在题目里记"属于哪些题库"，否则别人把共享题加进自己的题库时要改创建者的文档。
- **`latest` 冗余（④A）**：列表页不必逐行 `$lookup`；只在创建新版本时带条件更新，与版本集合不一致时可以重算。
- **版本号唯一索引**兼作并发保护：两人同时基于同一版本创建新版本，算出同一个版本号，后到者插入失败。
- **各集合独立的结构版本号（①B）**：只有 `surveys` 升到 2，users / responses / participations 结构没变，保持 1，不做无意义的迁移。校验器限制 `schemaVersion` 不超过当前代码的版本。

**新增索引**：

| 集合 | 索引 | 类型 | 服务的查询 |
|---|---|---|---|
| questions | `owner_updatedAt` `{ ownerId: 1, updatedAt: -1 }` | 普通 | 我的题目列表 |
| questions | `shared_updatedAt` `{ sharedWith: 1, updatedAt: -1 }` | 多键 | 共享给我的题目 |
| question_versions | `uniq_question_version` `{ questionId: 1, version: 1 }` | 唯一 | 按顺序列出版本历史；并发创建同一版本号时后到者失败 |
| question_banks | `owner_updatedAt` `{ ownerId: 1, updatedAt: -1 }` | 普通 | 我的题库 |
| question_banks | `shared_updatedAt` `{ sharedWith: 1, updatedAt: -1 }` | 多键 | 共享给我的题库 |
| surveys | `question_source` `{ "questions.source.questionId": 1, "questions.source.versionId": 1 }` | 多键 | 被哪些问卷使用；跨问卷统计第一步找问卷 |

跨问卷统计的第二步 `responses` 按 `surveyId: { $in: [...] }` 过滤，沿用阶段一的 `survey_submittedAt`，不用新建。阶段一的 5 个索引名称和定义都不变。

### 4.4 迁移与兼容（C7）

- **迁移机制（②C）**：[db/migrations.py](../db/migrations.py) 中按编号排列的步骤，由 `init_db` 在更新校验器、建索引之后依次执行；执行过的记入 `migrations` 集合，下次跳过。每一步本身也可重复执行（只改还没改过的文档），中途失败后重跑安全。001 为阶段一初始结构，由 `init_db` 建立，没有单独步骤。

### 4.5 题目与版本（第 2 段，2026-10-26 确认 ①B ②B ③B ④A ⑤A ⑥A ⑦A）

**接口**（`app/routers/library.py`，业务在 `app/services/library.py`）：

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| POST | `/api/questions` | 新建题目，同时生成 v1（kind = create） | 登录用户 |
| GET | `/api/questions?scope=mine\|shared` | 我的题目 / 共享给我的题目，按更新时间倒序 | 登录用户 |
| GET | `/api/questions/{id}` | 详情：最新版本摘要与完整内容、创建者、来源 | 可见 |
| DELETE | `/api/questions/{id}` | 软删除；版本保留，已使用它的问卷不受影响 | 创建者 |
| GET | `/api/questions/{id}/versions` | 版本历史，`parentVersion` 表示基于哪个版本创建 | 可见 |
| POST | `/api/questions/{id}/versions` | 基于 `baseVersion` 创建新版本（kind = edit） | 创建者 |
| GET | `/api/questions/{id}/versions/{n}` | 某个版本的完整内容 | 可见 |
| POST | `/api/questions/{id}/versions/{n}/restore` | 用 vn 的内容生成新版本（kind = restore，父版本为 vn） | 创建者 |
| POST | `/api/questions/{id}/fork` | 把某个版本（默认最新）复制为自己的新题，记录 `derivedFrom`（kind = fork） | 可见 |

"可见" = 创建者或被共享者；看不到的题一律 404（不透露是否存在），看得到但不是创建者做修改类操作返回 403。

**规则与理由**：

- **版本树（①B）**：新版本可以基于任意版本，`parentVersionId` 记录父版本，N4 例子中 v1 → v2 → v3 的关系、N5 的"A 问卷用旧题、B 问卷用新题"都能表达。旧内容从不被覆盖，因此不需要像阶段一编辑问卷那样用 `revision` 乐观锁防覆盖。
- **版本号分配（②B）**：取版本集合中最大版本号 + 1 插入，唯一索引 `uniq_question_version` 保证同一个号只有一个成功，撞号时重新取号（最多 5 次）。之后带条件 `latest.version < 新版本号` 更新摘要：并发时到达顺序不影响结果；若更新摘要前中断，下一次建版本时自动补上（版本号取自版本集合本身，而不是摘要）。
- **题型不变（③B）**：同一道题的各版本题型相同；要换题型就复制为新题。跨问卷统计要合并各版本的数据，单选与数字题的数据无法合并；问卷升级版本时跳转规则也因此不会失效。
- **选项 id 跨版本稳定（④A）**：与阶段一修改题目的规则相同，原有选项带 id 保持不变，新选项由系统生成；只接受基础版本里的 id。新 id 还会避开这道题所有版本用过的 id，删掉的旧选项不会和新选项被误认为同一个。这样跨问卷统计可以直接按选项 id 分组合并各版本。
- **拒绝空版本（⑤A）**：内容与基础版本相同不生成新版本；恢复的版本与最新版本相同也拒绝（409）。
- **软删除（⑥A）**：问卷里存的是快照，删除题目不影响任何问卷的填写和统计。
- **写入顺序与补偿（⑦A）**：新建（含复制）先插 v1 版本、再插题目；题目插入失败则删除刚插的版本。所有读取都从题目文档出发，不会看到"有题目没版本"的中间状态。与阶段一提交答卷失败时撤回参与记录的做法一致（单机 MongoDB 不支持多文档事务）。

**复用阶段一的代码（C6）**：请求格式直接用阶段一的 `QuestionIn`（四种题型的定义与中文提示）；题目自身的检查用 `check_question`；题目内容的组装与选项 id 处理从 `app/services/questions.py` 移到公共模块 `app/services/content.py`，阶段一的题目管理改为从那里导入，行为不变（原有测试全部通过）。

### 4.6 共享与题库（第 3 段，2026-10-26 确认 ①A ②A ③A ④A ⑤A）

**接口**：题目共享在 `app/routers/library.py`，题库在 `app/routers/banks.py`（业务在 `app/services/banks.py`）。

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| POST | `/api/questions/{id}/shares` | 把题目共享给某个账号 | 题目创建者 |
| DELETE | `/api/questions/{id}/shares/{username}` | 取消共享 | 题目创建者 |
| POST | `/api/banks` | 新建题库 | 登录用户 |
| GET | `/api/banks?scope=mine\|shared` | 我的题库 / 共享给我的题库 | 登录用户 |
| GET | `/api/banks/{id}` | 题库详情：每道题的最新版本摘要，按加入时间排列 | 可见 |
| PATCH | `/api/banks/{id}` | 修改名称、说明 | 题库创建者 |
| DELETE | `/api/banks/{id}` | 软删除，里面的题不受影响 | 题库创建者 |
| POST | `/api/banks/{id}/items` | 加入题目（只能是自己创建的题） | 题库创建者 |
| DELETE | `/api/banks/{id}/items/{questionId}` | 移出题目 | 题库创建者 |
| POST / DELETE | `/api/banks/{id}/shares[/{username}]` | 共享 / 取消共享题库 | 题库创建者 |

题目详情、题库详情中的 `sharedWith`（共享名单）只有创建者能看到，被共享者看到的是 null。

**可见规则**：看得到一道题 = 自己创建的，或直接共享给自己，或在某个未删除的、共享给自己的题库里。最后一条用一次查询 `question_banks.find_one({sharedWith: 我, deletedAt: null, "items.questionId": 题})` 判断，走 `shared_updatedAt` 索引（测试中用 explain 验证）。

**决定与理由**：

- **只有题库创建者能修改题库（①A）**：被共享者只能浏览和使用。允许多人编辑需要把 `sharedWith` 改成带角色的结构，还会牵出"编辑者能否再共享"等问题；团队协作可以由同事把题共享给题库创建者，后者复制为自己的题后加入。
- **只能把自己创建的题加入题库（②A）**：否则会"转手共享"——王老师只把题共享给小李，小李把它放进自己的题库再共享给小明，小明就看到了王老师从没共享给他的题。限制之后，通过题库看到的每道题都经过了它的创建者本人同意；要放别人的题，先复制为自己的题（`derivedFrom` 保留来源）。
- **"共享给我的题目"只列直接共享的题（③A）**：通过题库共享的题在"共享给我的题库"里按题库浏览，两种途径能用的题完全相同。列表因此只需一次走索引的查询，也不会出现同一道题在两处重复、分不清来源的情况。
- **删除题目时从创建者自己的题库移除（④A）**：`update_many` + `$pull`，只需查创建者自己的题库（题库里只有自己的题）。两步之间没有事务，所以题库详情也跳过已删除的题作为兜底。
- **按加入时间排列（⑤A）**：需求没有提到排序，不做调序。

**几条固定规则**：

- 取消共享（题目或题库）后，对方不能再查看或把题加入新问卷；已经用到这道题的问卷存的是快照，不受影响；对方之前复制出的题已归对方所有，也不受影响。
- 共享对象按账号指定：账号不存在 404，共享给自己 422，重复共享视为成功，超过 100 人 409；重复加入题库视为成功，超过 500 道 409。
- 加入 / 移出 / 共享 / 取消都是单文档原子操作；人数和题目数上限写进过滤条件（如 `sharedWith.99` 不存在、`items.499` 不存在），判断与修改一次完成，并发也不会超出上限（测试中 5 个、3 个请求同时争最后一个名额，只有一个成功）。条件不满足时再读一次文档给出具体原因，与阶段一的条件更新写法相同。
- 题库条目带加入时间，`$addToSet` 比较整个对象认不出重复，所以加入时用 `$push`，把"还没加入"（`items.questionId: {$ne: 题}`）写进过滤条件。

### 4.7 问卷接入题库（第 4 段，2026-10-26 确认 ①A ②A ③A ④A ⑤A）

**接口**（加在阶段一的 `app/routers/questions.py`，业务在 `app/services/survey_library.py`）：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/surveys/{sid}/questions/from-library` | 从题库选一道题（默认最新版本，可指定版本、是否必答）加入草稿问卷 |
| PUT | `/api/surveys/{sid}/questions/{qid}?libraryAction=detach\|new_version` | 阶段一的修改接口，扩展：来自题库的题改了内容时须选择方式 |
| PUT | `/api/surveys/{sid}/questions/{qid}/source` | 把来自题库的题换成另一个版本（升级、回退、换分支），仅草稿 |
| POST | `/api/surveys/{sid}/questions/{qid}/save-to-library` | 把问卷里的题存为题库新题并关联；已发布、已关闭的问卷也可以 |
| GET | `/api/surveys/{sid}`（阶段一） | 来自题库的题多返回 `library`：`available`（还能不能用）、`latestVersion`、`isLatest` |

**快照怎么生成**：版本内容（含选项 id）原样复制；题目 id 在本问卷内重新生成（答卷照旧引用它）；跳转规则在问卷里另行设置；加上 `source`。填写、提交、校验、跳转、按问卷统计因此一行不改；填写视图把 `source` / `derivedFrom` 和跳转规则一起去掉，填写者看不到题库来源。

**决定与理由**：

- **已发布问卷也能存入题库（①A）**：只新建题库题并给问卷里的题加上 `source`，题目内容一个字不改，不违反发布后锁定（X10）。阶段一的旧问卷因此也能并入跨问卷统计——这是"旧数据仍然可用"的一部分。写回带 `revision` 条件；期间问卷被改过就失败，并撤回（删除）刚建的题库题和版本。
- **同一道题库题在一份问卷里只能出现一次（②A）**：否则统计时说不清一份答卷该算哪一个。
- **改了内容必须显式选择方式（③A）**：未传 `libraryAction` 返回 409 并说明两种方式。`detach`：本问卷的题与题库脱钩，`source` 改为 `derivedFrom`（之后再改也一直保留）；`new_version`：基于本问卷所用的版本在题库建一个新版本（形成分支），问卷换成它的快照，题目 id、跳转规则保留，仅题库题的创建者可选，其他人返回 403 并提示选择只改本问卷；题型不能变（4.5 节③B），要换题型只能脱钩。阶段一的题没有 `source`，不需要这个参数，行为不变。
- **可以切换到任意看得到的版本（④A）**：对应 N5"不同问卷可以使用不同版本"。保留题目 id、是否必答、跳转规则；新版本删掉了跳转规则用到的选项时，阶段一的整份检查（`check_survey`）报出并拒绝。题库题被删除或取消共享后不能再切换（`library.available` 为 false），但问卷里的快照照常发布、填写。
- **是否必答是问卷自己的设置（⑤A）**：版本里的 `required` 只作默认值；判断问卷里的题是否仍与来源版本一致时只比较题型、标题、选项、校验规则（`content.COMPARED_FIELDS`），只改必答时保留 `source`。同一道题在 A 问卷必答、B 问卷选填很常见，必答与否也不影响答案的类型，跨问卷统计照样合并。数据库结构不用改。

**一致性**：所有对问卷的修改仍走阶段一的"读出 → 修改 → 整份检查 → 带 revision 写回"。"存为新版本"先建版本、再写回问卷；写回失败时题库里多一个完整、合法的版本，无害（反过来先改问卷则可能出现指向不存在版本的 `source`）。

**对阶段一代码的改动**：`questions.update_question` 增加 `libraryAction` 分支（无 `source` 的题走原逻辑）；`surveys.to_detail` 把 `source` 里的 ObjectId 转成字符串；填写视图多隐藏两个字段。阶段一的全部测试照常通过。

### 4.8 被哪些问卷使用（第 5 段，2026-10-29 确认 ①A ②A ③A）

**接口**：`GET /api/questions/{id}/usage`（`app/routers/library.py`，业务在 `app/services/survey_library.py`）。返回按版本分组的使用数量（`versions`）、自己的问卷详情（`mySurveys`：标题、阶段、所用版本、在问卷里是第几题、答卷数、是否最新版本），以及创建者才有的 `othersTotal`。

**一次聚合完成**：

```js
surveys.aggregate([
  { $match: { "questions.source.questionId": 题, deletedAt: null } },     // question_source 多键索引
  { $addFields: { position: { $indexOfArray: [ { $map: { input: "$questions",
                  in: "$$this.source.questionId" } }, 题 ] } } },          // 这道题在问卷里的下标
  { $project: { ownerId, title, status, settings, createdAt, position,
                source: <questions[position].source> } },
  { $facet: {
      mine:   [ { $match: { ownerId: 我 } }, { $sort: { createdAt: -1 } } ],
      others: [ { $match: { ownerId: { $ne: 我 } } },
                { $group: { _id: "$source.version", n: { $sum: 1 } } } ] } }
])
```

自己问卷的答卷数再用阶段一的 `response_counts`（`responses` 按 `surveyId $in` 分组计数，走 `survey_submittedAt`）一次算出。复杂度 O(log N + k)，k 为用到这道题的问卷数；同一道题在一份问卷里只出现一次（4.7 节②A），计数不会重复。测试中用 explain 验证走了 `question_source`。

**决定与理由**：

- **看得到这道题的人都能查，别人的数量只告诉创建者（①A）**：被共享者需要知道"我哪些问卷在用它、用的第几版、要不要切换"，但别人怎么用与他无关；创建者是唯一能改这道题的人，需要知道改动会影响多少份别人的问卷（N6 中"怕影响别人的问卷"）。别人的问卷一律不暴露标题（Y6、F1.7）。
- **已脱钩的题不算在用（②A）**：内容已与题库不同，改题库不影响它，统计也不合并。
- **不做批量升级（③A）**：使用情况里标出 `isLatest: false` 的草稿，用户逐份调用 4.7 节的切换接口；每次切换都可能因跳转规则冲突被拒绝，逐份操作能看到具体原因，也不会出现"部分成功"。

**N6"修改时可以决定是否创建新版本"的落地**：题库里修改一律生成新版本（4.5 节，旧问卷不受影响）；问卷里修改来自题库的题时由用户选"只改本问卷"或"存为新版本"（4.7 节）；本接口提供做决定所需的信息——改之前先看会影响谁、影响多大。

### 4.9 跨问卷统计（第 6 段，2026-10-29 确认 ①A ②A ③A ④A）

**接口**：`GET /api/questions/{id}/stats?version=&bucketSize=&page=&pageSize=`（`app/routers/library.py`，业务在阶段一的 `app/services/stats.py`）。看得到这道题的人都能调用，但只统计**他自己的**问卷（Y7、F1.7）；不传 `version` 时合并全部版本。

返回：参与的问卷数、总提交数、回答了这道题的答卷数（`answeredCount`，占比的分母，因跳转可能少于总提交数，沿用 X12）、各问卷分别多少（`bySurvey`），以及按题型：

| 题型 | 内容 |
|---|---|
| 单选 / 多选 | `options`：按选项 id 合并各版本的计数和占比（多选为被选次数，各项相加可超过 100%）；`versions` 标出选项出现在哪些版本，`otherLabels` 列出其他版本里不同的写法 |
| 数字 | 平均值（2 位小数）、最小值、最大值；`distribution` 为等宽区间分布（左闭右开），`bucketSize` 为区间宽度 |
| 文本 | `entries`：按提交时间倒序分页的内容，每条带来源问卷的标题；非匿名问卷带填写者 |

**两步聚合**：

```js
// 第一步：自己的哪些问卷用了这道题（question_source 多键索引）
surveys.aggregate([
  { $match: { "questions.source.questionId": 题, ownerId: 我, deletedAt: null
              /* 指定版本时再加 "questions.source.versionId": 版本 */ } },
  { $addFields: { position: <这道题在 questions 里的下标> } },
  { $project: { title, createdAt, position, anonymous: "$settings.allowAnonymous",
                localId: <questions[position].id>, source: <questions[position].source> } },
  { $sort: { createdAt: -1 } }
])
// 第二步：只读这几份问卷的答卷（survey_submittedAt 索引）
responses.aggregate([
  { $match: { $or: [ { surveyId: A, "answers.questionId": A 里的题目 id }, ... ] } },
  { $sort: { submittedAt: -1, _id: -1 } },
  { $unwind: "$answers" },
  { $match: { $or: <同上> } },
  { $facet: { bySurvey: [...], optionCounts: [...] | numbers: [...] | entries: [...] } }
])
```

- **按"问卷 + 题目 id"成对匹配**：题目 id 只在一份问卷内唯一，同一道题库题加进每份问卷时都生成新 id，只按题目 id 匹配会混进别的题。
- **数字题的分布要再聚合一次**：`$bucket` 需要事先给出区间边界，边界取决于最小值、最大值，所以先由 `numbers` 分支求出最小值、最大值，再用同样的 `$match`/`$unwind` 跑一次 `$bucket`。
- **指定版本时的 `$match`**：`questionId` 和 `versionId` 是对数组的两个独立条件，理论上可能落在不同的题上；但版本 id 只属于这一道题，含这个版本 id 的题必然也含这道题的 id，所以结果正确。
- **一份问卷的答卷都对应同一个版本**：只有草稿能切换版本、改题，草稿收不到答卷；已发布问卷存入题库时内容一个字不改（4.7 节），所以问卷当前的 `source.version` 就是它全部答卷所用的版本，答卷里不需要另存版本。

复杂度：第一步 O(log N + k)，k 为自己用到这道题的问卷数；第二步只读这 k 份问卷的答卷，与阶段一单份问卷统计的规模相同。测试中用 explain 验证两步分别走了 `question_source` 和 `survey_submittedAt`。

**选项怎么合并**（Y7）：第 2 段保证选项 id 跨版本保留、新选项的 id 不与任何版本用过的 id 重复，因此"同一个 id = 同一个选项"。

- 参与合并的版本是**问卷实际用到的版本**（数据只来自它们）；一份问卷都没用时取指定版本或最新版本，计数全为 0。
- 选项文字取包含它的最新版本；排列按最新版本的顺序，只在旧版本里的选项排在后面。
- 例：v1"大一 / 大二 / 大三"，v2 把"大二"改为"大二（含转专业）"、删掉"大三"、新增"研究生"。合并后为"大一 [1,2]、大二（含转专业）[1,2]（otherLabels: 大二）、研究生 [2]、大三 [1]"。用户看到 otherLabels 后，若认为改字改变了含义，可以用 `version` 分开看。
- 题库里新建了版本但还没有问卷用它时，显示的仍是数据实际对应的旧文字。

**决定与理由**：

- **等宽区间，宽度自动选取或自己指定（①A）**：自动宽度从 1、2、5 × 10^k 中选最小的、使区间数不超过 10 个的值；答案全是整数时宽度至少为 1（不会出现 17–17.5 这样的区间）。区间从宽度的整数倍开始，如 17–35 岁得到宽度 2、区间 16–18 … 34–36；传 `bucketSize=5` 得到 15–20 … 35–40。指定的宽度会分出超过 100 个区间时返回 422。`$bucketAuto`（每个区间人数相近）的边界是 17.3–19.8 这样的数，不适合"年龄分布"；按每个数值计数在取值多的题（如手机号）上会列出成千上万行。
- **给出各问卷分别多少（②A）**：都是自己的问卷，不涉及隐私；能看出总数由哪些问卷构成，例如某份问卷的数据特别多、拉高了平均值。
- **沿用每份问卷各自的匿名设置（③A）**：匿名问卷的答卷本来就没有 `respondentId`（X1、X3）。与阶段一单题统计一致，是否带出填写者以问卷**现在**的设置为准：`$lookup` 前用 `$cond` 判断答卷所属问卷是否在"非匿名问卷"列表中，不在就不查。
- **只支持"全部版本"和"指定一个版本"（④A）**：需求的例子是"总体分布"，合并全部版本即可满足；"某版本及其后续版本"要先遍历版本树，收益小。

**对阶段一代码的改动**：只在 `stats.py` 末尾新增函数，复用 `_round`、`_respondent`、`response_counts`；阶段一的单份问卷统计不变。阶段一的旧问卷把题存入题库（4.7 节）后，它以前的答卷自动计入，旧数据一行都不用迁移。

```js
const QID = "^q_[0-9a-f]{8}$";
const OID = "^o_[0-9a-f]{8}$";

const options = {
  bsonType: "array", minItems: 2,
  items: {
    bsonType: "object", required: ["id", "label"],
    properties: {
      id: { bsonType: "string", pattern: OID },
      label: { bsonType: "string", minLength: 1, maxLength: 200 },
    },
  },
};
// 按题型限制跳转规则可用的 op
const rulesWithOps = (ops) => ({
  items: { properties: { when: { properties: { op: { enum: ops } } } } },
});

const question = {
  bsonType: "object",
  required: ["id", "type", "title", "required"],
  properties: {
    id: { bsonType: "string", pattern: QID },
    type: { enum: ["single_choice", "multiple_choice", "text_input", "number_input"] },
    title: { bsonType: "string", minLength: 1, maxLength: 500 },
    required: { bsonType: "bool" },
    validation: { bsonType: "object" },
    jumpRules: {
      bsonType: "array",
      items: {
        bsonType: "object", required: ["when", "goto"],
        properties: {
          when: { bsonType: "object", required: ["op", "value"], properties: { op: { bsonType: "string" } } },
          goto: { bsonType: "string", pattern: "^(q_[0-9a-f]{8}|END)$" },
        },
      },
    },
  },
  oneOf: [
    { required: ["options"],
      properties: {
        type: { enum: ["single_choice"] },
        options: options,
        jumpRules: rulesWithOps(["eq", "in"]),
      } },
    { required: ["options"],
      properties: {
        type: { enum: ["multiple_choice"] },
        options: options,
        validation: { bsonType: "object", properties: {
          minSelect: { bsonType: "int", minimum: 0 },
          maxSelect: { bsonType: "int", minimum: 1 },
        } },
        jumpRules: rulesWithOps(["containsAny", "containsAll", "equals"]),
      } },
    { properties: {
        type: { enum: ["text_input"] },
        validation: { bsonType: "object", properties: {
          minLength: { bsonType: "int", minimum: 0 },
          maxLength: { bsonType: "int", minimum: 1 },
        } },
        jumpRules: { maxItems: 0 },
      } },
    { properties: {
        type: { enum: ["number_input"] },
        validation: { bsonType: "object", properties: {
          min: { bsonType: "number" },
          max: { bsonType: "number" },
          integer: { bsonType: "bool" },
        } },
        jumpRules: rulesWithOps(["eq", "ne", "gt", "gte", "lt", "lte", "between"]),
      } },
  ],
};

const validators = {
  users: { $jsonSchema: {

      createdAt: { bsonType: "date" },

  surveys: { $jsonSchema: {
    bsonType: "object",

      schemaVersion: { bsonType: "int", minimum: 1 },
```
